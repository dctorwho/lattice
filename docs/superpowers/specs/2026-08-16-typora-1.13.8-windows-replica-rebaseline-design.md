# Typora 1.13.8 Windows 复刻目标重订设计

## 1. 背景与目的

项目现有总目标使用“兼容 Typora 1.13.8 的主要功能和工作流”等表述。该表述只要求产品能够处理相同格式或完成相似任务，弱于用户确认的产品目标，也会允许界面、交互和功能范围以“基本兼容”或“已有替代方案”为理由产生已知差异。

本次目标重订把项目的最终目标明确为：使用独立实现和独立品牌，完整复刻 Typora 1.13.8 在 Windows 10/11 上可由用户观察到的产品表现。后续需求、设计、测试、迭代验收和发布结论都必须以这一目标为准。

本次工作是产品基线与规划治理调整，不直接开发 M1 功能，不推翻已经通过的 M0 工程基础，也不修改 M0 历史测试事实。

## 2. 已确认的产品目标

项目最终目标为：

> 独立实现一款面向 Windows 10/11 的本地 Markdown 桌面编辑器，完整复刻 Typora 1.13.8 的简洁设计风格、单栏混合编辑模型、界面布局、六套内置主题效果、功能、编辑交互、快捷键、设置、文件工作流、导入导出和 Windows 系统集成。

“复刻”是最终验收目标，“兼容”只是复刻结果中的一项属性。仅能打开相同文件、支持主要功能或提供相似工作流，不足以认定复刻完成。

## 3. 范围与边界

### 3.1 纳入范围

- Typora 1.13.8 Windows 版本可公开确认的窗口结构、菜单、侧边栏、编辑区、状态反馈和对话框行为；
- 单栏混合编辑体验，包括光标、选区、输入法组合、撤销、滚动、查找和源码模式连续性；
- Markdown 基础与高级语法的显示、编辑、源码保真和导出行为；
- 文件创建、打开、保存、另存、编码、换行、冲突、恢复和工作区流程；
- 图片、剪贴板、资源管理、主题、专注模式和打字机模式；
- 六套内置主题的视觉效果，以及公开用户主题接口的可观察行为；
- 设置、快捷键、语言、无障碍、打印、导入导出和 Windows 系统集成；
- Windows 10/11 下不同显示缩放、常见中文输入法和文件系统条件。

### 3.2 独立实现边界

- 使用独立产品名称、图标、Logo、安装包标识和品牌文案；
- 不复制 Typora 私有源代码、安装包、主题源文件或品牌素材；
- 六套内置主题使用项目自己的 CSS、字体策略和资源独立重现视觉效果；
- 公开页面、截图和视频只作为行为与视觉研究证据，不作为可直接打包的产品资源；
- 保留发布前知识产权与许可证复核。

### 3.3 平台与非目标

- 产品复刻范围仅限 Windows 10/11；
- 不实现 macOS、Linux 特有菜单、快捷键、窗口或系统集成行为；
- 不增加 Typora 1.13.8 不具有的云同步、账号、协作、AI 写作、插件市场、移动端或浏览器端能力；
- 不以复制 Typora 内部技术实现为目标，只复刻用户可观察结果。

## 4. 复刻依据

### 4.1 采用版本化证据基线

项目没有可运行的正版 Typora 1.13.8，因此采用公开资料建立可追溯的版本化证据基线。项目能够严谨承诺的是：对公开证据能够确认的 Typora 1.13.8 Windows 可观察界面和行为，做到无已知差异的完整复刻。

资料优先级为：

1. Typora 1.13.8 官方发布记录；
2. 能够确认适用于 1.13.8 的官方文档和官方截图；
3. 能够确认版本的公开视频或可信评测；
4. 版本不能完全确认、但能由多个独立来源交叉验证的资料；
5. 单一且无法验证的资料只登记为证据缺口，不直接形成确定的产品事实。

已确认可使用的官方入口包括：

- `https://typora.io/releases/stable`；
- `https://support.typora.io/Typora-on-Windows/`；
- `https://support.typora.io/Shortcut-Keys/`；
- `https://support.typora.io/About-Themes/`；
- `https://support.typora.io/Export/`。

官方支持页面是持续更新的活文档，不能只凭当前页面标题断言其所有内容都属于 1.13.8。每条观察都必须另外记录版本适用依据和采集日期。

### 4.2 证据台账

新增一份中文的 Typora 1.13.8 Windows 公开证据台账。每一行至少包含：

- 稳定证据 ID；
- 来源 URL 和采集日期；
- 来源类型；
- 适用版本及判断依据；
- Windows 适用性；
- 观察到的界面、参数或行为；
- 可信度：高、中、低；
- 对应需求、`COMP-*` 项、迭代和测试用例；
- 状态：未实现、已实现、存在差异、证据不足。

台账记录对公开资料的结构化观察、必要摘要和链接，不复制整篇受版权保护的页面或视频。对可能变化的页面记录采集日期、允许保存的内容摘要或内容指纹，并在可用时记录稳定归档链接。

### 4.3 未知与冲突处理

- 没有可靠资料的细节标记为“证据不足”，不得凭想象实现后宣称通过；
- 多个来源冲突时，优先采用版本更明确、平台更匹配、来源级别更高的证据；
- 无法消解的冲突进入复刻风险清单，并阻止受影响项目形成最终通过结论；
- 后续发现更可靠资料时，先更新证据、复刻矩阵和测试，再修改实现；
- 不回写历史证据结论，基线变更以新增修订记录体现。

## 5. 复刻验收模型

### 5.1 追踪闭环

每个复刻项目必须形成完整链路：

```text
公开证据 → 复刻要求 → 详细设计 → 自动或人工测试 → 测试证据 → 迭代通过结论
```

现有 `COMP-*` ID 保留，避免无价值的全量重编号，但其含义从“兼容项”加强为“复刻验收项”。现有 36 个 `COMP-*` 项和 99 个迭代测试用例只是初始清单；完成证据盘点后必须审查粒度并按需追加 ID 和测试，不能用现有数量证明范围完整。

### 5.2 五层验收

1. **功能验收**：命令、设置、快捷键、文件工作流、导入导出及结果一致；
2. **交互验收**：光标、选区、IME、撤销、滚动、菜单、弹窗和状态反馈一致；
3. **视觉验收**：窗口结构、尺寸、间距、字体、颜色、六套主题和各种状态具有明确对照；
4. **数据安全验收**：未编辑字节、编码、换行、恢复和冲突保护不得退化；
5. **Windows 验收**：Windows 10/11、显示缩放、文件关联、安装、卸载、升级和系统集成通过。

视觉自动化采用项目自身的确定性截图和布局测量，公开参考截图用于人工对照和参数提取。不得把外部参考图直接变成项目发布资产。对动画、输入法、系统对话框和难以稳定像素比较的行为，使用结构化步骤、事件结果和人工签署共同验收。

### 5.3 发布通过条件

M8 最终通过前必须满足：

- 所有已经确认的复刻项均为 `passed`；
- 已知产品差异为零；
- 影响核心功能、数据安全、主要交互或主要视觉的高、中可信证据缺口为零；
- 每个视觉和交互项目都有对照依据及所需人工签署；
- 低可信资料没有被悄悄升级为产品事实，残余不确定性被明确记录；
- 数据安全、安全边界、构建、打包和发布门禁全部通过。

`documented_gap` 可以描述暂时风险或证据不足，但不能替代已知复刻项的发布通过。

## 6. 迭代结构

项目继续只使用 M0 至 M8 共九个迭代，不增加任务级状态、任务级报告或 `T01` 一类执行单元。

| 迭代 | 修正后的复刻责任                                                       |
| ---- | ---------------------------------------------------------------------- |
| M0   | 工程、安全、依赖、CI、打包和证据治理基础                               |
| M1   | 文件创建、打开、编码、保存、另存、冲突、恢复和源码模式                 |
| M2   | 单栏混合编辑器、基础 Markdown、光标、选区、IME、撤销和查找             |
| M3   | 窗口布局、标题栏、菜单、侧边栏、文件树、文章列表、大纲、搜索和窗口行为 |
| M4   | 表格、公式、图表、代码块、YAML、目录、脚注和 HTML 等高级 Markdown      |
| M5   | 图片、剪贴板、资源管理、六套内置主题、用户主题、专注和打字机模式       |
| M6   | 打印、HTML、PDF、图片，以及可选 Pandoc 导入导出                        |
| M7   | 设置、快捷键、语言、无障碍、性能，以及跨迭代视觉和行为差异清零         |
| M8   | Windows 安装、卸载、升级、文件关联、CLI、签名准备和正式发布验收        |

每个迭代继续使用三个入口文档和两个出口文档。每个迭代必须关闭自己范围内的已知差异，不能把前序未完成工作集中推迟到 M7。M7 只负责跨模块整合、全量回归和难以局部验证的差异收口。

M1 至 M8 都需要人工复刻门禁。迭代只有在自动化测试、适用视觉比较、数据安全测试和人工验收全部完成后，才能从 `awaiting_manual` 进入 `passed`。

## 7. 当前节点与历史完整性

- M0 已通过的工程、安全、依赖、CI 和打包成果继续有效；
- M0 历史 `04-test-report.md` 和 `05-exit-report.md` 不因目标重订而改写；
- 单独记录本次产品目标重订决策，并说明 M0 证明的是工程基础而不是最终界面复刻完成；
- 在 M1 开工前完成一次总计划复刻基线重订；
- 基线重订期间不把 M1 设置为 `in_progress`，也不开发 M1 产品功能；
- 重订完成并通过规划验证后，M1 仍是唯一可从 `ready` 转为 `in_progress` 的迭代；
- M2 至 M8 继续按依赖顺序保持 `blocked`。

因此，目标重订不会制造第十个迭代，也不会把已经关闭的 M0 重新拆分或回滚。

## 8. 架构与数据流影响

以下架构规则保持不变：

- Markdown 源字符串是唯一文档权威；
- CodeMirror 6 是编辑表面；
- 源码模式和混合模式共享文档状态、选区、历史和滚动模型；
- 未触及字节、BOM、编码、换行、空白和 Markdown 布局保持不变；
- Electron 渲染进程保持沙箱和无 Node 集成；
- 特权操作只通过经过运行时验证的窄 IPC；
- Pandoc 保持可选，核心编辑、构建和测试不依赖 Pandoc。

新增的是复刻基线数据流，而不是 Typora 实现依赖：

```text
公开资料
  ↓
证据台账
  ↓
复刻验收矩阵
  ↓
M0–M8 入口文档
  ↓
实现与测试
  ↓
测试报告和出口报告
```

证据台账只影响需求、设计和验收，不进入最终用户文档数据，不赋予渲染进程新的网络或文件权限。

所有新增或修改的项目文档、测试报告和出口报告使用中文。历史归档保持原样；M0 历史报告不做事实重写。

## 10. 机器验证要求

规划验证器需要新增或加强以下检查：

- 每个复刻项都有至少一条适用证据、所属迭代和测试映射；
- 每条强制证据都能追踪到复刻项，避免孤立台账记录；
- 已知差异不能通过 `documented_gap` 直接获得发布通过；
- 视觉项目包含窗口条件、显示缩放、主题、状态、对照证据和评估结果；
- 测试报告逐项记录自动化及人工结果；
- M1 至 M8 的人工门禁不能被文档或状态关闭；
- M8 为 `passed` 时不存在已知差异和关键证据缺口；
- M0 历史报告保持可验证，目标重订不伪造历史执行证据。

实施时采用测试驱动方式：先用规划验证测试证明旧规则会错误接受弱目标、孤立复刻项或未关闭差异，再修改验证器和文档使其通过。

## 11. 风险与控制

| 风险                               | 控制措施                                                               |
| ---------------------------------- | ---------------------------------------------------------------------- |
| 官方活文档内容晚于 1.13.8          | 记录采集日期、版本依据和发布记录关联，不把当前页面全部视为 1.13.8 事实 |
| 第三方视频或截图版本不明           | 降低可信度，并要求多来源交叉验证                                       |
| 视觉复刻被误解为复制素材           | 只提取可观察参数，独立编写 CSS 和资源，不打包外部参考素材              |
| 现有 `COMP-*` 粒度不足             | 保留已有 ID 并追加新 ID，不通过重编号掩盖覆盖缺口                      |
| M7 承担过多延期工作                | 每个迭代出口强制关闭本迭代已知差异                                     |
| 目标调整导致 M0 历史失真           | 保留历史报告，新建重订决策，不回写旧证据                               |
| 无正版参考程序导致绝对等同不可证明 | 对公开证据范围作出严格承诺，对证据不足保持显式且诚实的风险状态         |

## 12. 被否决的方案

### 12.1 继续只按官方功能清单实现

可信度高但覆盖不足，无法支持界面、视觉和细微交互复刻，不能达到确认后的产品目标。

### 12.2 无差别收集并采用网络截图和视频

覆盖较广，但容易混入其他版本、其他平台、第三方主题或修改后的界面，无法形成可靠验收基线。

### 12.3 采用版本化证据基线

这是确认采用的方案。它同时保留官方资料的权威性、第三方资料的补充价值和版本不确定性的显式控制，并能建立从资料到测试报告的完整追踪链。

## 13. 完成标准

目标重订完成必须同时满足：

- 总目标统一为 Typora 1.13.8 Windows 可观察产品表现的完整复刻；
- 独立品牌、独立实现和 Windows 10/11 平台边界清晰；
- 公开证据台账建立并通过机器覆盖检查；
- 复刻矩阵、M1 至 M8 入口和测试策略完成同步；
- 所有未来迭代启用人工复刻门禁；
- M0 历史证据未被改写，M1 仍未提前开工；
- 不再存在允许已知复刻差异直接通过发布的活跃规则；
- 文档、验证器聚焦测试和完整项目门禁全部通过；
- 所有新写或修改的报告和设计资料使用中文。
