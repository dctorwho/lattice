# 活跃文档中文化设计

## 1. 目的

本次修改的目的，是让项目中承担说明、设计、计划、测试和验收职责的活跃资料统一以中文呈现，使中文团队可以直接阅读、执行和审查，而不需要在中英文结构之间切换。

中文化不得改变产品范围、架构约束、需求含义、用例参数、迭代状态或验收结论。它是一项文档治理调整，不是 M1 功能开发，也不会改变 `iterations/state.json` 中 M1 的 `ready` 状态。

## 2. 范围

### 2.1 纳入范围

以下活跃资料全部改为中文：

- 根目录的 `README.md` 和 `AGENTS.md`；
- `docs/` 下除历史归档外的产品、架构、技术、开发、测试、验收和运行手册；
- `docs/superpowers/specs/` 与 `docs/superpowers/plans/` 中仍由项目引用的设计和实施计划；
- `docs/test-cases/` 下的活跃测试说明与夹具目录；
- `iterations/README.md`；
- `iterations/templates/` 下的五类迭代模板；
- M0 至 M8 的需求、详细设计和测试用例；
- 已存在的 M0 测试报告和迭代出口报告；
- `iterations/state.json` 中供人阅读的证据摘要。

### 2.2 排除范围

以下内容不做翻译：

- `docs/archive/` 下的历史归档和历史证据；
- `.superpowers/` 下的临时审查记录和过程性草稿；
- 源代码、测试代码中的普通标识符和内部错误消息，除非它们专门定义文档结构契约；
- 构建产物、依赖目录和第三方文件。

## 3. 保持不变的稳定值

下列内容保持原值，必要时在中文句子中直接使用：

- 迭代、需求、兼容性和测试用例 ID，例如 `M1`、`DOC-001`、`COMP-001`、`TC-M1-001`、`MAN-M1-001`；
- 文件路径、命令、脚本名、包名、版本号、哈希、网址和 Git 提交号；
- 状态枚举，例如 `blocked`、`ready`、`in_progress`、`awaiting_manual`、`passed`、`failed`；
- GitHub 检查上下文，例如 `quality`、`codeql` 和 `dependency-review`；
- 技术专名，例如 Electron、React、CodeMirror、Markdown、Pandoc、IPC、SBOM 和 CodeQL；
- 代码块、JSON 键、接口名、配置键和命令输出原文。

稳定值保持不变，可以避免翻译导致链接失效、状态模式不匹配、命令不可执行或证据无法核验。

## 4. 中文文档结构契约

迭代报告不保留英文展示结构。模板、实例文档、验证器和测试同时迁移到以下中文契约：

- `## 自动化用例结果`
- 表头：`用例 ID | 结果 | 证据 | 备注`
- `## 人工用例结果`
- 表头：`用例 ID | 结果 | 评估人 | 证据`
- `## 需求完成矩阵`
- 表头：`全局 ID | 要求结果 | 完成证据 | 结果`
- `## 最终迭代结论`
- 机器结论行：`结论：passed`

其中 `passed` 仍是稳定状态值。验证器必须严格验证中文标题、中文表头、ID 精确集合、非空证据、评估人和最终结论，不能同时接受已经废弃的英文结构，以免形成两套活跃契约。

测试用例入口表的标题与表头也迁移为中文，解析器仍按列角色而不是自然语言猜测含义。每个模板必须生成可被验证器直接识别的中文实例。

## 5. 翻译规则

### 5.1 语义保真

- 按段落和表格单元格翻译，不删减需求、失败模式、参数矩阵、证据要求或停止条件；
- 保留 `M0` 至 `M8` 的原有边界、依赖和验收职责；
- 保留所有数字、阈值、版本、文件格式、边界值和平台条件；
- 保持 Markdown 链接目标、锚点用途和代码块内容有效；
- 不借中文化引入新功能、新依赖或未来迭代占位实现。

### 5.2 表达规范

- 标题、说明、表头、注释性文字和证据摘要使用简体中文；
- 技术专名首次出现时可以使用“中文说明 + 英文专名”，后续保持行业通用写法；
- 命令、路径、代码、状态值和标识符使用反引号包裹；
- 避免逐词直译，优先使用清晰、可执行、可验证的中文表达；
- 不使用“待定”“TBD”“TODO”等未解决占位词。

## 6. 实施边界

本次工作分为三个相互约束的部分：

1. 文档层：翻译所有纳入范围的自然语言和展示结构；
2. 契约层：把规划验证器使用的固定标题、表头和结论行迁移为中文；
3. 测试层：先以失败测试证明旧验证器不能识别中文契约，再实现中文契约并验证英文旧结构被拒绝。

文档迁移和验证器迁移必须在同一次变更中完成，避免任何时刻以“文档无法通过规划验证”的状态作为交付结果。

## 7. 验证策略

完成后执行以下有限检查：

1. 清点纳入范围的 Markdown 文件，确认没有遗漏；
2. 扫描活跃资料中的英文结构标题、英文表头和连续英文说明段落；
3. 检查 `docs/archive/` 没有发生内容修改；
4. 运行规划验证器的聚焦单元测试；
5. 运行实时规划文档验证，确认 M0 至 M8、测试用例和需求覆盖数量不变；
6. 运行格式、差异空白和链接检查；
7. 运行完整 `pnpm check`。

英文扫描只用于定位未翻译的自然语言，允许稳定值、专名、代码块、命令、路径和引用的原始输出存在。最终以人工抽查和机器契约检查共同判断完成度。

## 8. 完成标准

满足以下条件才算完成：

- 所有纳入范围的文档和报告均以中文作为唯一叙述语言；
- 活跃迭代模板和报告不再依赖英文标题或英文表头；
- 所有稳定 ID、状态、命令、路径和证据值保持准确；
- 历史归档没有被改写；
- M0 仍为 `passed`，M1 仍为 `ready`，M2 至 M8 的依赖状态不变；
- 规划验证器、聚焦测试和 `pnpm check` 全部通过；
- 不存在未解决占位内容或因翻译产生的断链、表格错列和语义缺失。
